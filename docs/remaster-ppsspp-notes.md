# PPSSPP texture pipeline reconnaissance

Source inspected: PPSSPP `b9c5b28b8f69a78a18bdf381fb4d34b703d21e97` (local `ppsspp/ai-remaster`). These are source findings, not yet runtime measurements.

## Identity and source pixels

`TextureCacheCommon::ApplyTexture()` constructs the in-memory cache key from texture address, dimensions and CLUT hash (`GPU/Common/TextureCacheCommon.cpp:533,591`). `TexCacheEntry::CacheKey()` masks the address, packs dimensions, and folds in CLUT hash for indexed textures (`GPU/Common/TextureCacheCommon.h:502-513`). The content hash is computed on creation and recheck in `ApplyTexture()` (`TextureCacheCommon.cpp:700-725,930-939`). Its algorithm **changes when replacement or saving is enabled**: `ComputeTextureHash()` delegates to `TextureReplacer::ComputeHash()` (`TextureCacheCommon.cpp:402-409`), whose selected `quick`/`xxh32`/`xxh64` and hash-range options come from `textures.ini` (`TextureReplacer.cpp:321-358,554-653`). Therefore a durable AI identity must record the game ID, replacement key `(entry->CacheKey(), entry->fullhash)`, and the hash policy/version; a bare address or current default `fullhash` is insufficient. `ReplacementCacheKey` and the on-disk `%016llx%08x` name are in `GPU/Common/ReplacedTexture.h:67-95` and `TextureReplacer.cpp:1029-1038`.

The shared GLES/D3D11 decode path is `TextureCacheCommon::LoadTextureLevel()` (`TextureCacheCommon.cpp:3045-3116`). Immediately after `DecodeTextureLevel()` at line 3080, `pixelData` has decoded pixels and `decPitch`, but may be 16-bit or CLUT8 unless `TexDecodeFlags::EXPAND32` is requested (`3065-3078`), and may be a temporary buffer when CPU scaling is enabled (`3058-3063`). The existing texture-save notification after scaling (`3099-3114`) carries the replacement identity, dimensions, format and pitch; `TextureReplacer::NotifyTextureDecoded()` copies pitched rows to owned memory before queueing an I/O task (`TextureReplacer.cpp:807-905`). A hook for **original decoded RGBA** belongs after decode and before scaling, with explicit `EXPAND32` handling or a separate conversion; reusing the existing notification unaltered may capture already scaled pixels.

Vulkan bypasses `LoadTextureLevel()` and decodes in `TextureCacheVulkan::LoadVulkanTextureLevel()` (`GPU/Vulkan/TextureCacheVulkan.cpp:955-1014`). Its upload loop uses that helper for ordinary textures and directly copies replacement levels (`643-915`); its existing save notification is at `865-882`. A common capture callback must be invoked in both decode paths (or inside `DecodeTextureLevel()` with sufficient identity context). `TextureScalerCommon::ScaleAlways()` (`GPU/Common/TextureScalerCommon.cpp:560`) is downstream scaling, not an identity/capture point.

These calls are synchronous with each backend's texture build/upload path, which is reached from `ApplyTexture()` (`TextureCacheCommon.cpp:939`); they are **not** PPSSPP's worker task. PPSSPP can run a separate `EmuThread` depending on graphics context (`Core/EmuThread.cpp:39-79,130-144`), so do not hardcode an OS thread name. Treat this as GPU/cache owner-thread code: copy bytes and immutable metadata before returning; never retain `pixelData`, upload memory, `TexCacheEntry *`, or `ReplacedTexture *` in an AI job. The existing save task's row-copy pattern is a useful model, though it copies on the cache path and must be budgeted.

## Replacement consumption and publication

`TextureCacheCommon::PrepareBuildTexture()` calls `FindReplacement()` before deciding size/levels (`TextureCacheCommon.cpp:2816-3042`, especially `2966-3012`). `TextureCacheCommon::FindReplacement()` excludes volume and video textures, builds the exact `ReplacementCacheKey`, and calls `TextureReplacer::FindReplacement()` (`1771-1800`). The replacer resolves an alias/filename, caches hits and misses, and creates a `ReplacedTexture` (`TextureReplacer.cpp:654-735`). `ReplacedTexture::Poll()` schedules its file decode on `g_threadManager`; the task calls `Prepare()` and changes state to `ACTIVE` or `NOT_FOUND` (`ReplacedTexture.cpp:80-107,172-333`). While pending, PPSSPP keeps the original texture and marks `TexStatus::TO_REPLACE`; a later `ApplyTexture()` detects `ACTIVE` and rebuilds the GPU texture (`TextureCacheCommon.cpp:635-666,1802-1833`). GLES, D3D11 and Vulkan use the same `PrepareBuildTexture()` decision, but their upload implementations differ (`GPU/GLES/TextureCacheGLES.cpp:204-333`, `GPU/D3D11/TextureCacheD3D11.cpp:241-339`, `GPU/Vulkan/TextureCacheVulkan.cpp:643-915`). This is the existing normal upload path to reuse.

**Same-session publication is absent from that path today.** `TextureReplacer::LoadIni()` scans filenames / parses aliases when loading a pack (`TextureReplacer.cpp:144-260`); `FindReplacement()` stores negative results in `cache_` (`654-706`). Dropping a generated PNG in the directory does not refresh aliases or cached misses. `TextureReplacer::NotifyConfigChanged()` only reloads on certain enable/save transitions (`91-133`), and reload waits for outstanding file tasks through `DeleteVFS()`/`Unload()` (`135-142`, `ReplacedTexture.cpp:122-137`). The smallest production change appears to be an owner-thread publication API in `TextureReplacer`: receive a completed immutable key/path, update its alias and negative cache entry, then signal the matching `TexCacheEntry` for a subsequent replacement lookup/rebuild. Alternatively, an explicit reload after publication is suitable for a first smoke test or next-session proof, but must be measured for stalls. **This API and same-session signaling are design proposals, not existing functions.** Do not mutate replacer maps from the AI worker; put publication onto the cache owner thread. Write completed cache files atomically before publishing so `Prepare()` cannot see a partial image.

PPSSPP's existing replacement convention is under `DIRECTORY_TEXTURES/<game ID>` (`TextureReplacer.cpp:91-105`), with hash-named PNG files and optional `textures.ini` aliases (`TextureReplacer.cpp:266-317,373-428`). `TextureReplacer::LoadPackForTesting()` can load a chosen directory without global config (`TextureReplacer.cpp:82-89`). `g_paramSFO.GetDiscID()` is read by the replacer on configuration change (`TextureReplacer.cpp:91-92`); homebrew/fake IDs need a defined policy before persistent AI cache layout.

## Invalidation and eligibility

Content rehash in `ApplyTexture()` detects source changes and replaces or moves cache entries (`TextureCacheCommon.cpp:700-818`). CPU/block-transfer invalidation marks overlapping entries `HASH_RECHECK` (`2757-2797`). Framebuffer notifications mark `FRAMEBUFFER_OVERLAP` (`1159-1206`); `ApplyTexture()` checks framebuffer candidates **before** building an ordinary texture (`840-879`). A capture hook in ordinary build therefore naturally excludes direct framebuffer sampling, but it should still reject overlap and recheck dynamic behavior. `IsVideo()` delegates to `gpu->IsVideo()` (`1155-1157`), and both `FindReplacement()` and `PrepareBuildTexture()` exclude known video/PPGe/CLUT8 GPU-indexed cases (`1771-1787,2879-2980`). No single status bit certifies that all other textures are static. Frequency of content-hash changes and repeat sightings should be part of eligibility.

Normal GPU cache clearing and device loss run through `TextureCacheCommon::Clear()` (`2715-2753`); replacing a source does not itself invalidate a disk AI result unless the persistent key includes the content hash and model/settings metadata. `TextureReplacer::Decimate()` purges decoded replacement data but keeps lookup objects (`TextureReplacer.cpp:907-940`). Model version, preprocessing, output scale, and hash policy should be in the AI cache namespace; PPSSPP's filename key alone does not encode them.

## Options to reuse and risks to test

- Existing configuration: `bReplaceTextures` and `bSaveNewTextures` are per-game config settings (`Core/Config.cpp:739-740`), with UI controls in `UI/DeveloperToolsScreen.cpp:95-96` and `UI/GameSettingsScreen.cpp:379`. Saving enables the decoded notification but also disk PNG dumping; a production AI hook needs its own cheap gate. The comment mentioning `bReplaceTexturesAllowLate` at `TextureCacheCommon.cpp:1778` has no corresponding option in the inspected config, so do not design around it.
- Reuse the exact `ReplacementCacheKey` and `TextureReplacer` hash policy where interoperability with texture packs matters. Prefer `xxh32` or `xxh64` for generated assets and define collision handling; `ignoreAddress`/`reduceHash` are rejected with `quick` (`TextureReplacer.cpp:347-356`). `hashranges`, `reducehashranges`, `ignoreAddress`, and mipmap behavior can alter identity or visible extent (`TextureReplacer.cpp:431-551,554-653`).
- Capture cost includes row copies and possible 32-bit expansion on the texture upload path. Test pitched and 16-bit textures, CLUT variants, mip levels, scaling enabled/disabled, Vulkan's hardware scaling branch, and game changes. Avoid holding GPU upload pointers after the function returns.
- Same-session activation needs an explicit signal for entries that already recorded `NOT_FOUND`: their `TO_REPLACE` flag is cleared (`TextureCacheCommon.cpp:635-666`) and negative lookup is cached (`TextureReplacer.cpp:699-706`). A positive file appearing on disk alone will not trigger a retry.
- A file pack may be zip-backed (`TextureReplacer.cpp:144-175`); generated files should use a separate owned directory or an explicit provider rather than assume writable pack storage. Invalidation/reload must account for pending VFS tasks.

Then implement and time a narrow owner-thread publication hook for same-session activation. Record original-vs-replacement frame captures and CPU cache-path time for the first sighting, pending frames, and cache hit.
