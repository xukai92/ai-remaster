# Remaster validation ladder

Use this alongside `SPEC.md` and `PLAN.md`. The first experiment is an **unmodified PPSSPP baseline and a small legal texture fixture**, followed by a deterministic fake enhancer. A real model is evaluated only after the cache and replacement path work end to end.

## Test workload and evidence

Build one redistributable PSP homebrew scene with source code and generated textures in this project. It should show a stationary textured 3D quad or cube with a 64×64 or 128×128 checker/label texture, a second eligible texture, a tiny texture that must be skipped, and a deliberately changing texture. Give it a fixed camera, fixed animation or frame counter, and a command to exit after a fixed frame count. Add a static frame dump (`.ppdmp`) only if its capture and redistribution rights are clear. Keep commercial assets, games, and dumps out of the repository.

Record the fixture source hash and built ELF/PRX hash. Keep the same PPSSPP commit, build mode, graphics backend, resolution, fixture, settings, and capture window across paired runs. Record OS, CPU/GPU, driver, power profile, compiler, and cache location; on Steam Deck record whether AC power, TDP limit, and shader warmup were controlled. A result from desktop Linux is a desktop baseline, not a Steam Deck claim.

PPSSPP already provides `PPSSPPHeadless` with `--graphics=software|vulkan`, `--screenshot-save`, `--screenshot`, `--screenshot-diff`, `--max-mse`, and wall timeout; see `ppsspp/headless/README.md`. Software rendering is useful for deterministic reference images, but verify the integration on the actual Vulkan replacement path. Its `--bench` reports average speed, so it does **not** replace per-frame pacing data. Build C++ tests with `-DUNITTEST=ON` and run `PPSSPPUnitTest all`; run PPSSPP's existing HLE suite as `python test.py -g --graphics=software` (`-g` excludes known expected failures). Frame dump regression tests use `ppsspp/frametests.py` and `ppsspp/docs/frametest.md`. For short headless game runs, follow `ppsspp/AGENTS.md`: Release build, Vulkan, `--timeout-wall=30` unless justified, and assert that the scene actually rendered. Exact command flags should be checked against the built binary before automation is written.

Use distinct run modes: **off** (feature disabled), **cold** (feature enabled, empty remaster cache, fake backend), and **warm** (feature enabled, cache retained from a successful cold run). Keep PPSSPP's ordinary shader/cache state consistent across modes. Repeat each mode at least five times after one warmup run, alternating the order of off and warm runs to reduce thermal drift. Run cold with a fresh remaster cache each time. Report every run, median, spread, and p50/p95/p99 frame time; never report a single favorable run as representative.

## Milestone gates

| Gate | What to run | Pass evidence |
|---|---|---|
| 0. Upstream baseline | Build unmodified PPSSPP; run the fixture with the feature absent; run its unit and `-g` autotest suites; capture a fixed frame and performance trace. | Build and tests complete, fixture renders, reference screenshot and machine/build manifest exist, and exact proposed capture/replacement hook points are documented. No remaster code is needed yet. |
| 1. Core and fake backend | Standalone core tests on small synthetic RGBA images, including alpha, stride, bad dimensions, duplicate requests, queue saturation, worker exception, and shutdown with queued work. | No PPSSPP headers in core; fake output is byte deterministic with checked hash/dimensions; one job per duplicate identity; pending jobs and copied source bytes stay within configured limits; failures return a reason and never terminate the process. |
| 2. Persistent cache | Two separate process runs against a temporary cache; inject truncated image, wrong metadata/model version, invalid path components, and interrupted temporary file. | First run invokes fake backend and atomically stores a validated artifact; second run produces a hit with zero backend calls and matching bytes; every corrupt/mismatched case becomes a miss or safe regeneration; no partially written final artifact is accepted. |
| 3. PPSSPP adapter | Run off, cold, and warm with the fixed homebrew scene on Vulkan; capture logs/counters, cache artifact hash, and screenshot on first and later load. | Off matches the upstream reference under the same settings; cold displays original before enhancement completes, records an eligible capture and completed background job; later load/session displays the unmistakable fake replacement; warm has cache hits and zero inference for unchanged eligible textures; tiny/dynamic/framebuffer cases have explicit skip reasons. Feature path failures retain original rendering. This is **Gate A** before ML work. |
| 4. Real backend spike | Same synthetic/legal image set at 64, 128, 256, and 512 square; run each candidate runtime/model on the intended hardware and document license. | At least one candidate produces valid 2×/4× output, preserves or correctly restores alpha, reports model version, recovers from init failure, and has measured load time, latency, memory, and visual comparison. Select only after evidence; no fixed latency promise is assumed. This is **Gate B**. |
| 5. MVP | Repeat off/cold/warm traces using the selected backend; side-by-side captures at base, high internal resolution, existing PPSSPP scaler, and AI replacement; run acceptance items 1–13 in `SPEC.md` §18. | All 13 items have linked evidence; trace reports frame pacing, cache-hit cost, inference latency, memory and disk size; visual examples support the product value decision. This is **Gate C**. |
| 6. Robustness | Slow fake backend, many unique/dynamic sources, rapid quit/relaunch, corrupt cache, backend failure; repeat under sanitizers where practical. | Queue/copy-memory/disk policies stay within configured bounds; no render-thread inference, crash, race, partial final artifact, or unbounded dynamic-content job stream; off path still matches baseline. |
| 7. Portability design | Map one second emulator's source identity and replacement lifecycle to the implemented core API. | Document required adapter calls and capability gaps; classify changes as adapter-only, small core extension, or redesign before a port. This is **Gate D**. |

## Measurement contract

Add counters or buffered trace events only when implementation reaches the relevant milestone. Give each run an ID and record feature mode, game ID, PPSSPP SHA, backend/model/config version, fixture hash, and cache directory. Use a monotonic clock for durations. Keep high-volume trace output buffered or sampled so logging itself does not dominate the render thread.

| Measure | Collection method | Check |
|---|---|---|
| Scene reached | Increment a frame-present counter and a known fixture-texture observation counter; save a screenshot. | Both counters positive and image contains the fixture. An all-zero error log alone is insufficient. |
| Frame pacing | Timestamp consecutive presents in the same scene window; report p50/p95/p99 frame interval and >16.67 ms / >33.33 ms counts, plus raw frame times. Pair off/cold/warm runs. | No statistically credible material regression from enqueue or cache lookup. Before running, declare an allowable delta using baseline run-to-run variation and product tolerance; investigate any sustained p95/p99 or long-frame-count increase. The spec's <0.2 ms submission and <0.1 ms lookup are initial engineering targets, not pass guarantees. |
| Submission and lookup | Time only the synchronous adapter sections (capture/copy/enqueue and cached lookup), with counts and p50/p95/p99. Exclude worker time. | No backend inference or synchronous disk decode on the render/emulation critical path. Report observed tail costs; inspect outliers by texture size and cache state. |
| Cache behavior | Count seen, eligible, hit, miss, submitted, coalesced, dropped, skipped by reason, completed, failed, and replacement loaded; hash artifact contents. | Cold: miss → one completed job → valid artifact. Warm: hit → replacement loaded, with zero new inference for the same identity/model/config. Identity remains stable across sessions and mip levels do not collide. |
| Worker cost | Timestamp backend start/end per source size; sample process RSS (for example `/usr/bin/time -v` or `/proc/<pid>/status`) and GPU memory if supported; record cache bytes. | Latency and peak memory are reported by size and model. Queue source-image memory has a configured cap; disk use follows the selected cache policy. |
| Rendering correctness | Compare fixed screenshots with headless exact comparison where deterministic; otherwise retain reference, diff image, and a declared MSE tolerance for one pinned backend/driver. Inspect the fake marker in the expected region. | Off should match upstream in deterministic software/reference tests; cold original and warm fake output should be distinguishable in the expected texture region. Do not expect exact cross-driver GPU screenshots. |

For a pacing comparison, save the raw frame intervals and calculate per-run summary statistics, then compare the distribution of run summaries across modes. A confidence interval or full spread is more useful than a claim based on one p99. The precise tolerance must be chosen before looking at the new result; if baseline noise is larger than the intended budget, stabilize the machine or mark the measurement inconclusive. A correctness failure blocks progression regardless of a good benchmark.

## Minimum result record

For each gate, save a short result note under `docs/results/` with: date; gate; pass/fail/inconclusive; commands; PPSSPP and fixture SHAs; hardware/software manifest; test counts; links to logs, screenshots, raw traces, and artifact hashes; known limitations; next action. Large generated caches and raw game assets stay outside Git. Do not label a gate passed when the workload failed to reach the capture/replacement path.
