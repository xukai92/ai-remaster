# Synthetic PSP texture workload

This is a source-only, CC0-1.0 homebrew fixture for PPSSPP capture, replacement, and frame-time experiments. All pixels are generated by `main.c` at startup or from the frame number. It contains no game assets, fonts, model weights, or recorded frames. The four fixed-camera 3D panels, left to right, are:

| Panel | Source | Expected policy role |
| --- | --- | --- |
| 1 | 128×128 checker with a white border | Stable eligible texture |
| 2 | 64×64 two-axis gradient with a white border | Second stable eligible texture |
| 3 | 8×8 red/dark checker | Tiny skip case |
| 4 | 64×64 color pattern updated every frame at the same PSP address | Dynamic skip case |

The camera and geometry are fixed. The default run renders 180 frames, then exits. The changing panel uses only the integer frame number, so repeated runs have the same content on the same frame. A screenshot request is sent to PPSSPP after frame 60 (or on the last frame of a shorter run). This uses PPSSPP's `kemulator:` screenshot devctl, which a real PSP may ignore; it does not alter the scene.

## Build

Install a PSPSDK/pspdev toolchain so `psp-config`, `psp-gcc`, and `psp-fixup-imports` are on `PATH`. One pinned Linux x86-64 acquisition path is the [official PSPDEV v20260801 release](https://github.com/pspdev/pspdev/releases/tag/v20260801). From this repository's root:

```sh
mkdir -p /tmp/ai-remaster-pspdev
curl -fL https://github.com/pspdev/pspdev/releases/download/v20260801/pspdev-ubuntu-latest-x86_64.tar.gz \
  -o /tmp/ai-remaster-pspdev/pspdev-ubuntu-latest-x86_64.tar.gz
printf '%s  %s\n' \
  7a6cb2de21bfbc1d4aa06d10d0a45c547dedc8f6e1c8fc7ff8c7ba6eee667ee6 \
  /tmp/ai-remaster-pspdev/pspdev-ubuntu-latest-x86_64.tar.gz | sha256sum -c -
tar -xzf /tmp/ai-remaster-pspdev/pspdev-ubuntu-latest-x86_64.tar.gz \
  -C /tmp/ai-remaster-pspdev
export PSPDEV=/tmp/ai-remaster-pspdev/pspdev
export PATH="$PSPDEV/bin:$PATH"
```

This archive is built for Ubuntu. Other Linux distributions may need compatible host libraries for the toolchain binaries. On this NixOS host, `psp-gcc` additionally needed `libmpc.so.3`, `libmpfr.so.6`, `libgmp.so.10`, and `libzstd.so.1` on `LD_LIBRARY_PATH`; these were supplied by Nix packages `libmpc`, `mpfr`, `gmp`, and `zstd` during the verified build.

Then build:

```sh
make -C tests/workload clean
make -C tests/workload -j2
sha256sum tests/workload/main.c tests/workload/Makefile tests/workload/remaster_fixture.elf
```

`make` also creates `tests/workload/EBOOT.PBP`. Keep the generated ELF/PBP and object files out of Git. Record the PSPSDK version or commit and the built ELF SHA-256 with each result; the ELF hash is compiler-dependent. This fixture has no external input files.

## Run

Use an unmodified, Release `PPSSPPHeadless` from the pinned PPSSPP checkout. Check its `--help` output for the local binary's supported flags. For example, from the repository root:

```sh
mkdir -p tests/workload/output
ppsspp/build-headless/PPSSPPHeadless tests/workload/remaster_fixture.elf \
  --graphics=software --timeout-wall=30 \
  --screenshot-save=tests/workload/output/reference.png
sha256sum tests/workload/output/reference.png
```

The expected console markers are `REM_FIXTURE start frames=180` and `REM_FIXTURE done frames=180`; `reference.png` should visibly show all four panels. A file's existence alone does not prove that the scene rendered, so inspect the image and markers. For the later replacement-path experiment, rerun the same ELF with `--graphics=vulkan` and keep backend, resolution, PPSSPP commit, settings, and screenshot frame fixed across off/cold/warm runs. Use `--timeout-wall=30` on short headless runs. The screenshot request occurs after the frame-60 buffer swap; the default run continues to frame 180 for a stable measurement window.

The default 180-frame exit does not require an argument. When a launcher passes PSP program arguments through, `--frames N` accepts `1..3600`; invalid values fall back to 180. Do not rely on this optional argument for a headless baseline until the launcher is verified to forward it.

## Reproducibility and limits

Record the source, Makefile, and ELF SHA-256 values, PPSSPP SHA, toolchain version, graphics backend, renderer settings, host CPU/GPU/driver, and cache path with every captured run. The two stable textures have separate pixel buffers and dimensions. The changing texture retains one buffer address while its content changes each frame. A future adapter must establish from actual logs whether each texture reaches its capture and replacement hooks; visual appearance alone cannot establish eligibility or dynamic filtering. A software screenshot provides a deterministic visual baseline, while Vulkan is needed to verify the intended replacement path.

The fixture was authored for this project. No prebuilt ELF is included; build it with a recorded toolchain version and hash the output. A successful build alone does not prove that the scene rendered.
